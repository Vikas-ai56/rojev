rojev · v1 review · updated 2026-11-03

A robot you can talk to while it works

rojev is a System 1 / System 2 robot runtime. A vision-language-action model (S1) moves the arm. A vision-language model (S2) decides what each thing the person says means for the running task. Between them, a state owner is the only component allowed to change what the robot does. v1 uses only frozen open-source models, with no training, in the RoboCasa365 kitchen simulator (a Franka arm on a mobile base).

The problem

Why talking to a moving robot is hard

A VLA policy takes camera images, the robot's state and one task sentence, and returns a chunk of actions: here 16 actions, 0.8 s of motion at 20 Hz. It does what it was trained on, one task per sentence. A person next to the robot changes their mind, interrupts and makes remarks while the arm moves. That raises five problems:

ProblemWhat it looks like on the robot
TimingControl needs an action every 50 ms; a model answer takes 0.5–1 s. Every answer describes a world that has already moved.
Partial informationThe person has spoken, but for about a second nobody knows what they meant, and the arm may be about to grasp.
RevisionThe goal changes halfway through a motion.
Compute allocationWhich model runs when, on what deadline, and what happens when it is late or silent.
CommitmentHow much of a predicted chunk to execute before asking the model again.
Goal 1

Interruptible execution

The person can say wait, stop, go on or name another task while the arm moves. Each line becomes a typed decision with a probability per option. Raw text never reaches the VLA.

Goal 2

Long tasks from trained skills

No new motor skills. A task, composite ones included, is one of the task sentences the VLA was trained on. System 2 chooses and switches between them.

Why frozen models: the runtime and the decision logic can be tested without training confounds. Each model sits behind a fixed interface, so a trained part can replace it later without touching the runtime.

Approach

A robot model should never read raw speech

Speech straight into the VLA

“make it fast pls” → task text

Happened in an early live test. A VLA only understands sentences like the ones it was trained on, so a remark became its goal.

Speech into a typed decision first

“make it fast pls” → continue

Jev picks from a closed list. A new task can only be one of the trained task sentences. In testing, 4 of 5 speed requests were read as continue, and no user words ever reached XR-1.

  • Fast and slow kept apart, as in Figure's Helix (a 7B S2 at 7–9 Hz over an 80M S1 at 200 Hz) and Hi Robot. S1 streams actions at 20 Hz; S2 decides at about 1 Hz and never blocks motion.
  • Nothing stale, unclear or unanswered moves the robot. Late actions are skipped, stale decisions refused, unanswered changes paused.
  • Proposal ≠ command ≠ running. S2 proposes, the owner commands, the robot side confirms what is actually running.
  • Hesitate between consequences, not labels. “Stop” and “wait” both pause the robot, so being unsure between them is no reason to ask.
  • Safety in code, not in models. A guard inside the control loop pauses the arm when anything above it goes quiet.
Architecture

How System 1 and System 2 fit together

Solid: control flow. Dashed: camera frames and confirmations. Every part runs on its own thread, and nothing waits for a model. The simulator runs on a laptop; XR-1 and OneJev run on a remote GPU.

Control loop and guard

Moves the arm, and stops it if anything goes quiet

  • Every 50 ms: apply one action, take a new camera frame. Everyone reads only the newest frame.
  • The guard pauses the arm if actions stop arriving for 0.5 s, or the owner goes silent for 2 s, even if everything else has crashed.
Execution runtime

Decides what is actually running

  • Each chunk is timed from the frame it was computed on. Actions that are already late are skipped, never replayed, and new chunks blend in smoothly.
  • Late actions happen only in real time. In lockstep the world waits for XR-1, so nothing is ever late. A real robot cannot pause physics: the arm keeps moving while XR-1 thinks, so the start of every chunk is already in the past when it arrives. Stopping the arm on every request instead would mean a 0.5 s pause every 0.8 s.
  • When the person speaks, the arm keeps moving, but actions that cannot be undone are frozen until the meaning is known. Each robot declares which those are; on this Franka it is the gripper.
S1 runner

Keeps actions flowing

  • Measures how long XR-1 takes and asks for the next chunk early enough that the arm never runs out.
  • An answer too late to be useful is dropped and asked again on the newest frame.
State owner

The only part that can change the plan

  • Every user line, model proposal and robot confirmation passes through it. Decisions made before the person last spoke are refused.
  • No answer within 1 s → the robot pauses and says so. A late answer is still applied to the moment it was about. “Stop” and “wait” stay in force until the person says otherwise.
System 2 · Jev

Turns one user line into one decision

  • It offers OneJev only the reactions that make sense right now. While moving: continue, switch task, wait, ask, stop. While paused: resume, keep holding, switch task, ask, stop.
  • Reactions are grouped by what they do to the robot, and Jev asks the person only when the top two groups are close. keeps moving: continue, resumepauses: wait, stop, ask, keep holdingchanges task: switch
  • After “switch task”, a second question picks one of XR-1's trained task sentences, or none. XR-1 only ever sees that sentence, never the user's words.
One event, end to end

“wait”, then “go on”

A recorded run: XR-1 closing a toaster-oven door, with Jev listening. Times are simulated seconds.

TimeWhat happens
0.0 sThe whole task sentence goes to XR-1, which starts moving.
3.0 sThe person types “wait”. The owner acknowledges at once, freezes the gripper while the arm keeps moving, and asks Jev. Simulated time stops while OneJev thinks.
3.05 sJev answers wait (88 % probability). The robot pauses and remembers the task it interrupted.
6.0 s“go on”. The robot is paused, so the options are now resume, keep holding, switch task, ask, stop.
6.05 sresume (72 %). The interrupted task is re-issued and XR-1 starts moving again.
10.5 sThe task succeeds, as the simulator sees it. Nothing in S2 knows it is done: v1 has no completion signal (see v2).
How we got here

Approaches we tried

1 · OneJev picks every next step for π0.5², MJev checks

dropped

task→list of possible next steps→MJev checks them on the image→OneJev picks one→π0.5² does it

How it did: OneJev picked the right next step 40 % of the time (its 0.8B version 22.5 %). On new tasks, a quarter of the steps needed had never appeared as exact phrases in π0.5²'s training data, so they could not even be offered.

Why we moved on: too unreliable to steer every step, and the robot model plans its own steps better. S2's job shrank to answering the person.

2 · The robot model: SmolVLA → π0.5² → XR-1

replaced

SmolVLA→π0.5²→XR-1

How it did: SmolVLA solved 4 of 20 test episodes. π0.5²'s own step planner seemed to flip between “fridge” and “freezer” and fail multi-step tasks, but those runs turned out to have broken camera images, so that evidence was withdrawn and never re-run. XR-1 had the best published result (57 %) and matched it in our runtime (18 of 20).

Why we moved on: SmolVLA was too weak; XR-1 was the strongest open model with numbers we could reproduce. π0.5² is still supported as an option.

3 · MJev and SAM 2 as “is it done?” checkers

dropped

camera frame→MJev / OneJev: is this step done?·SAM 2 tracks the object→is it inside?

How it did: on 222 kitchen scenes labelled by the simulator, MJev and OneJev were at chance (50 % and 52 % balanced accuracy); MJev never once said “done”. SAM 2 tracked well from a good start, but a bad first mask never recovered, and its “inside the freezer” check was wrongly “done” 90 % of the time.

Why we moved on: no better than chance. MJev left the loop; SAM 2 is kept for measurement only.

4 · Commit-and-verify

off

π0.5² proposes a step→pin it→release when checked done, or after 25 s

How it did: step flip-flopping fell from 19 switches to 2, but with no working checker nothing was ever confirmed, and a wrong first step stayed pinned until the 25 s limit. These runs also had the broken camera images.

Why we moved on: it needs a working done checker, and XR-1 does not report its steps. The code is built and switched off.

5 · Now: S1/S2 runtime, Jev answers only changes

current

XR-1 runs the whole task·person speaks→Jev picks one reaction→owner applies it

How it does: matches XR-1's published results (18 of 20); reads 55 of 82 user lines right, and “stop” / “go on” 4 of 4 after grouping reactions by effect; 17 of 19 fault scenarios pass.

Still missing: knowing when a task is done, and running in real time. That is v2.

Robot modelXR-1Best published open result on RoboCasa365 when chosen in October 2026: 57 % across the 50-task test set, far ahead of π0.5 on multi-step tasks. Inside our runtime it matched its own published test episodes, 18 of 20 against the authors' 20 of 20.

Composite tasks

Long tasks today

A composite task is given to XR-1 as one trained sentence, and XR-1 runs it end to end. System 2 decides which trained sentence is in force: the person can switch to another trained task mid-run, and Jev maps their words onto that sentence.

WhatResult
Three composite tasks, no speech, one run eachBoil the kettle 24.3 s · wash the lettuce 41.8 s · store leftovers in a bowl 87.6 s, all succeeded

Composite tasks never seen in training have not been tested in our setup yet; the XR-1 paper reports 32 % on them. In v1 the task options are a short hand-written list per run.

Known issues

What v1 does not handle yet

The scene has to match the sentence

RoboCasa always builds each scene so the task sentence is true: for the kettle task, the kettle is always on the counter. A real kitchen makes no such promise. XR-1 would still reach for where kettles usually were, and nothing in v1 first checks whether the task is possible, or already done.

No step-by-step understanding

XR-1 runs the whole sentence by itself, with no planner. Its 32 % on unseen composite tasks comes from that alone. When it goes wrong it stalls, repeats a finished step or does steps in the wrong order, and nothing in the system notices.

No “done”

Nothing knows when a task has finished. After a task had succeeded, “go on” restarted it.

Real time over a long network link

The loop works in lockstep. In real time, with the GPU on another continent, the arm ran out of actions on two thirds of ticks. XR-1 has to run close to the robot.

The robot model is environment-specific

This XR-1 checkpoint was fine-tuned on RoboCasa demonstrations for the Franka. A different kitchen or robot needs fine-tuning on that robot's own demonstrations, and the “done” model will likely need tuning on the new setting too.

Limits of the decision layer

Jev can switch only to tasks from a short list per run, and its confidence threshold is a chosen default, not fitted. “are you done?” once stopped a working robot, and only English is handled.

v2 is aimed at the first three.

Next

v2: new multi-step tasks, and knowing when they are done

Goal: run composite tasks the robot has never seen as a whole, built from skills XR-1 already has, and finish them cleanly. New objects and kitchens come as a byproduct. No new motor skills or new robots in this phase.

Why: v1 cannot tell when a task is done, cannot tell whether a task can be done from where the robot is, and can only switch to tasks from a short hand-written list.

A critic that watches the robot planned

One vision-language model that, for any task sentence, answers three things: how far along it is, whether it is done, and how likely XR-1 is to succeed at it from here. The last answer is the missing “can this task run now?” check.

A supervisor that uses it planned

On the planning side: ends the task when the critic says done, retries when progress stalls, and never moves on without done. Steering XR-1 step by step is added only if it beats XR-1 running the whole sentence.

Step 1, no training

Start from frozen progress models (RynnValue-4B or Robometer-4B), with the “done” threshold set on simulator-labelled frames from kitchens kept aside for testing.

Step 2, train the critic if step 1 falls short

The bar: catch at least 70 % of completions at no more than 5 % false “done” on unseen tasks. If the frozen model misses it, fine-tune Robometer-4B with LoRA (about 1–2 GPU-days). Labels come free from the simulator's own success check on every frame, with failed runs and frames after success as negatives. The “can XR-1 succeed from here” answer is trained by running XR-1 3–5 times from the same state and using the success rate as the label.

Step 3, train the robot model only if needed

If XR-1 does much worse when starting where a previous step left off (a drop of more than 30 points), fine-tune it on those in-between states.

How we know it worked

On unseen composite tasks, success beats plain XR-1 by at least 5 points, with under 1 % wasted motion after the task is done. Unseen tasks and kitchens are never used for training or for setting thresholds.

Later

Fine-tune XR-1 for a second robot (SO-101). A learned S2 → S1 link like Helix's, only if it beats this setup.

Code map

Where to look in the repository

The core is the rojev/ package; robot- and model-specific code sits beside it in executors/ and services/. Packages import one way, bottom to top, and a test enforces it. A suggested reading order:

rojev/protocol/Shared message types: observations, commands, confirmations, proposals.
rojev/robot/Robot interface: action limits, which actions are irreversible (the gripper), a MuJoCo SO-101.
rojev/control/execution.py (what is running), guard.py, loop.py.
rojev/system1/runner.py (action supply), commit.py (how much of a chunk to run), monitor.py, remote.py.
rojev/system2/jev/ (the decision layer), models/onejev.py, worker.py.
rojev/owner/state_owner.pyThe state owner.
rojev/transport/Connections to the remote models.
